# P2 Research — Per-Agent (Per-Role) Behavioral Baseline

**Status:** research / decision doc (not implementation). Drives the P2
`ember-agent-monitor` extension that backs `smb_envelope::monitor::BehavioralBaseline`.
**Owner consumer:** `ember-smb-platform` (plan §3a insider model, §8.6 open question).
**Co-input consumer:** Whale Signal (interface must stay neutral, not SMB-shaped).

> Read order: this doc → `src/spectral/{baseline,profile,motif,distance}.rs`
> → `design/agent-monitor-spec.md` §4/§5 → SMB `docs/plan-of-record.md` §3a/§8.6
> → `crates/envelope/src/lib.rs` `mod monitor`.

---

## 1. Problem

`ember-agent-monitor` today ships **one global spectral envelope**
(`Baseline::default_baseline()` in `src/spectral/baseline.rs`), calibrated
against `threat-intel/calibration/clean_corpus/` — i.e. *coding* sessions
(edit-test loops, debug-explore reads, refactors). The whole notion of
"normal" is a single band on three quantities.

P2 needs **per-role** normal-behavior profiles for SMB *domain* agents
(receptionist, quoter, scheduler, dispatcher, …) so that "this employee is
acting strange" is detectable **per principal**, not just against a global
coding-shaped envelope. A receptionist that suddenly starts reading the
quote database and fanning out to network egress is anomalous *for a
receptionist* even though each action is individually within global bounds
and no v0.5 pattern rule fires. That is the §3a insider signal: the agent
uses its *legitimate* privileges in a structurally abnormal way.

Concretely, three gaps (all named in SMB plan §3a / §8.6):
1. No per-role/per-principal notion of normal — only the global envelope.
2. No identity hook — `Baseline` is keyless; nothing keys a profile to an `AgentId`.
3. No cold-start story — a freshly-issued agent (plan §3a lifecycle) has zero history.

This doc maps the feature set onto the **existing** spectral machinery,
lays out the design space with explicit forks, and recommends a default.

## 2. What exists today (grounded in source)

### 2.1 Spectral primitives (`src/spectral/`)
- **`profile.rs` — `SpectralProfile::from_session(graph)`** computes, per
  session graph: `n_nodes`, full `eigenvalues` of the normalized-symmetric
  Laplacian, `fiedler_value` (λ₂), a 30-point log-spaced `heat_trace` Θ(t)
  on [1e-2, 1e2], and a fitted `spectral_dimension` (slope of log Θ vs log t
  in the plateau). This is the per-session fingerprint and the natural
  per-role feature vector backbone.
- **`laplacian.rs` — `build_session_laplacian`** builds the graph: nodes are
  events *minus* housekeeping kinds (drops `SessionStart/End`, `Finding`,
  `Intervention`); edges are causal (`parent_event_id`), and a **trust-zone
  crossing is weighted 2.0 vs 1.0** for same-zone (spec §3). So the spectrum
  already encodes "how much this agent crosses trust boundaries."
- **`baseline.rs` — `Baseline` + `Envelope`** is the current "normal":
  `fiedler: Envelope`, `spectral_dimension: Envelope`,
  `heat_trace_samples: Vec<(t, Envelope)>`. `Envelope::deviation(value)`
  returns the one-sided distance outside `[low, high]` (0 inside).
  `Baseline::score(profile) -> SpectralScoreBreakdown { total, fiedler_dev,
  spectral_dimension_dev, heat_trace_dev }`. Loads/saves JSON via the in-house
  writer; user override at `state/user/spectral_baseline.json`, regenerated by
  `ember-agent calibrate`. **This is the struct to generalize from `1` to
  `1-per-role`.**
- **`distance.rs`** — `heat_kernel_distance(p1, p2)` is a **size-invariant**
  comparator on log-Θ (responds to deviation from the power law, not its
  scale — exactly right for comparing sessions of different lengths against a
  role centroid). `davis_kahan_ratio(L_old, L_new)` is an *a-priori* change
  predictor `‖δL‖_F / λ₂` — a cheap per-step "did the graph just structurally
  shift" signal that needs no second eigendecomposition of the new graph.
- **`motif.rs` — `check_motifs(profile)`** matches the session spectrum
  against an 8-entry attack-shape catalog (exfil paths, credential-harvest
  stars, cycles, bipartite amplification). Role-independent attack shapes;
  complementary to baseline, not replaced by it.

### 2.2 How detection consumes it today (`src/detect/mod.rs`)
- `DetectConfig` holds `spectral_baseline: Option<Baseline>`
  (`Some(default_baseline())`), `spectral_cadence: 5`, `spectral_threshold: 0.5`.
- The `spectral_anomaly` rule runs every `event_count % cadence == 0`,
  scores the current `SpectralProfile` against the single baseline, and emits
  a finding when `total > threshold`. Findings are then filtered by
  `min_score: 0.30`.
- **Single global `Baseline` is threaded through one `DetectConfig`.** Per-role
  means: resolve *which* `Baseline` by the acting `AgentId`'s role before
  scoring. That is the entire structural change on the detect side.

### 2.3 Intervention ladder (`types.rs` + spec §5)
- `InterventionMode { Observe, Warn, Block }` is a **global proxy config, not
  per-session** (spec §5 "Configuration scope" — the in-line validation found
  per-session mode to be a bug). Escalation thresholds: 5 consecutive blocks →
  session-level concern; 20 cumulative → terminate (spec §5).
- The deviation **score** is what should drive position on the ladder; the
  *mode* stays the operator's global floor. (See §5.3.)

### 2.4 The trait the platform consumes (`crates/envelope/src/lib.rs`)
```rust
pub struct BehaviorSample { pub dimension: String, pub value: f64 }   // opaque sample + label
pub enum Assessment { Normal, Deviant { score: f64, dimension: String } }
pub trait BehavioralBaseline {
    fn observe(&self, agent: &AgentId, sample: BehaviorSample);
    fn assess(&self, agent: &AgentId) -> Assessment;
}
pub trait Quarantine { /* quarantine / is_quarantined, BlastRadiusExceeded guard */ }
```
Key facts to honor:
- The interface is **already per-`AgentId`** and **already spectral-agnostic
  at the boundary** ("the core engine is spectral; the interface is a neutral
  opaque sample plus a label"). The dimension/value pair is the neutral edge;
  the spectral profile is an implementation detail behind it.
- `Assessment::Deviant { score, dimension }` is a *scalar* deviation + the
  attributing dimension — matches `SpectralScoreBreakdown`'s per-term
  attribution (fiedler / spectral_dimension / heat_trace) one-to-one.
- `AgentId(String)`, `TenantId(String)` exist; `PrincipalId::Agent(AgentId)`.
  **No role type exists yet** — the role↔baseline mapping is net-new (§4, fork F1).

### 2.5 The honest gap
`observe`/`assess` are an **online, per-agent, dimension-labelled** contract.
`Baseline`/`score` are a **batch, global, fixed-3-dimension** implementation.
P2 is the bridge: keep the neutral online trait, back it with per-role spectral
baselines and a cold-start prior.

## 3. Design space

### 3.1 What features should define a role's baseline?

The role baseline is a distribution over a **feature vector** computed from
the role's session graphs. Four feature families, mapped to what already exists:

**(A) Spectral shape of the action graph — REUSE `profile.rs` verbatim.**
The core of the baseline. Per role, store the envelope (or centroid +
spread) of:
- `fiedler_value` (λ₂) — community structure / convergence onto a target.
- `spectral_dimension` — chain-like vs tree-like vs hub-like execution.
- `heat_trace` samples Θ(t) at canonical t — multi-scale connectivity, the
  size-invariant fingerprint. Compare with `heat_kernel_distance` to a role
  centroid profile (size-invariant: a receptionist's 6-event and 40-event
  sessions both compare cleanly).
- *(optional)* the leading-k eigenvalue band, for finer roles.
This family needs **no new math** — `Baseline` already carries exactly these
three envelopes; per-role just means one `Baseline` per role.

**(B) Action-type / event-kind distribution — NET-NEW (small).** The spectrum
is *topology-blind to labels*: a read→transform→write path and a
prompt→tool→result path can share a spectrum. Roles differ sharply in their
*mix* of `EventKind` (`ToolCall`/`ToolResult`/`SubagentInvocation`/
`InterAgentMessage`/`UserPrompt`) and `Capability` (`FileRead`, `NetworkOut`,
`EmailSend`, `CredentialAccess`, …). A receptionist is mostly
`UserPrompt`/`ModelText`/calendar `ToolCall`; a quoter reads pricing data and
writes quotes. Store a per-role categorical distribution over event-kind and
capability classes; score new sessions by divergence (e.g. L1 / Jensen-Shannon)
from the role's reference histogram. **This is the single most important
net-new feature** — it catches "right shape, wrong verbs" (a receptionist
whose graph still looks tree-like but is now full of `CredentialAccess` +
`NetworkOut`). Cheap: counting, not eigendecomposition.

**(C) Peer / tool usage profile — PARTLY THERE.** Which peers an agent
messages (`InterAgentMessage`, `SubagentInvocation`) and which tools/MCP it
calls. The trust-zone-crossing edge weight (`laplacian.rs`, 2.0 vs 1.0)
already pushes cross-boundary structure into the spectrum, so (A) captures
*how much* boundary-crossing happens. Capturing *which specific peers/tools*
(a receptionist that suddenly talks to the finance agent) is an
adjacency/set feature, adjacent to (B). Recommend: ship as a set-membership
feature in P2 only if (A)+(B) underperform on the peer-pivot case; otherwise
defer (Simplicity First).

**(D) Egress cadence — REUSE the event stream, NET-NEW aggregation.** Rate and
burstiness of outfacing actions (`NetworkOut`, `EmailSend`, egress-gate
submissions). The monitor already emits a tool-call event stream (spec §6);
the egress gate (`egress/mod.rs`) sees every `OutfacingAction`. A role has a
characteristic egress tempo (a scheduler sends N confirmations/hour; a
receptionist rarely egresses unprompted). This is a **temporal** feature the
spectral profile does *not* capture (the graph is causal-topological, not
timed). Model as an EWMA of egress-events-per-window with per-role control
limits (see §3.2 prior art). Strong insider signal: data exfil shows up as an
egress-cadence spike before it shows up as a shape change.

> **Feature-set recommendation:** ship **(A) spectral + (B) event/capability
> distribution + (D) egress-cadence EWMA** in P2; hold (C) peer-set as a
> fast-follow. (A) reuses `Baseline` as-is per role; (B) and (D) are the
> net-new signal that makes the baseline *role-discriminating* rather than
> just *coding-vs-not*. Each maps to one `BehaviorSample.dimension` string at
> the trait boundary (`"spectral.fiedler"`, `"dist.capability_js"`,
> `"egress.cadence"`, …) so `Assessment::Deviant.dimension` stays meaningful.

### 3.2 Calibration: online vs batch, and cold start

**Batch (today).** `ember-agent calibrate <events.jsonl>` → recompute envelopes
from a corpus. Clean, reproducible, CHANGELOG-gated. But: a role's first
agents have no corpus, and SMB agents drift (a quoter learns new products).

**Online (the trait asks for it).** `observe(agent, sample)` is a streaming
contract. Per the SPC/EWMA prior art ([EWMA streaming AD], [AnEWMA]), the
standard, cheap, bounded-memory online normal is an **EWMA mean + EWMA
variance per (role, dimension)**, with control limits at mean ± k·σ. This is
the right engine for (B) and (D), and works for the scalar spectral quantities
in (A) too. EWMA's known weakness (volatility to transient spikes) is exactly
what we *want* dampened, and the probabilistic-EWMA variants ([Carter &
Streilein]) down-weight anomalous observations so an attack doesn't poison the
baseline it's being measured against — **adopt that guard** (don't update the
running stats from a sample that scored as `Deviant`, or update with reduced
weight).

**Cold-start — the crux.** A freshly-issued agent (plan §3a) has no history.
Three seeding strategies, not mutually exclusive:
- **Population/role prior (RECOMMENDED default).** Seed a new agent from the
  **role-level** aggregate of all prior agents in that role (this tenant first,
  then cross-tenant role prior if tenancy policy allows — see fork F4). This is
  textbook **hierarchical / partial-pooling**: the prior art ([hierarchical
  shrinkage], [GLAD]) shows partial pooling "shrinks toward panel-level ranges
  when evidence is weak while preserving heterogeneity as observations
  accumulate" — i.e. a new agent *is* its role until it earns its own profile.
  Implement as: per-agent estimate = shrinkage·(role prior) + (1−shrinkage)·
  (agent's own EWMA), with shrinkage → 0 as the agent's sample count grows.
- **Seed-from-prior-agents.** Special case of the above when the role prior
  is literally the mean of retired/peer agents of the same role.
- **Warm-up grace period.** For the first W sessions, run the role at a
  **lower interventon ceiling** (observe/warn only, never block) regardless of
  score, so a still-forming baseline can't weaponize false positives into a
  DoS — this directly serves the §8.6 blast-radius requirement. After W, the
  agent's own profile dominates the prior.

**Cross-tenant caution (per-server tenancy).** SMB tenancy is **per-server**
(plan §8.2, hard isolation). A cross-tenant role prior therefore cannot be a
live read across tenant servers. Options in fork F4 — the default is a
**shipped, static role prior** (a "receptionist starter profile" baked from
internal/synthetic corpora, like today's `default_baseline()` but per role),
which needs no cross-tenant data flow and respects isolation.

### 3.3 Deviation score → assessment → intervention

- **Score:** reuse `Baseline::score` for (A) → `SpectralScoreBreakdown`. For
  (B)/(D), the per-dimension EWMA control-limit exceedance is the deviation
  (same shape as `Envelope::deviation`: distance outside the band, 0 inside).
  Combine into one `Assessment`: report the **max-deviation dimension** as
  `Deviant { score, dimension }` (so the operator sees *what* tripped), and
  optionally keep the vector for the rationale. `heat_kernel_distance` to the
  role centroid is an alternative single spectral scalar if the three-envelope
  decomposition proves too coarse for a role (fork F2).
- **Per-step early signal:** `davis_kahan_ratio` between the pre/post-event
  Laplacian gives a cheap "structural transition imminent" flag without a full
  re-score — good for tightening cadence when the graph is shifting.
- **Feeding the ladder (spec §5):** the global `InterventionMode` stays the
  operator's floor (`Observe`/`Warn`/`Block`). The per-role **score** maps to a
  position *at or below* that floor via thresholds (analogous to the existing
  `spectral_threshold`), e.g. score in `[t1,t2)` → warn-class finding, `≥t2` →
  block-class. Crucially: a baseline deviation is **not** an automatic block —
  it is a *finding with a score*, contextualized like every other detection
  (spec §4: `pattern × source_trust_inverse × severity`). Quarantine
  (`Quarantine::quarantine`) is the escalation past block and **must** respect
  the blast-radius bound (`BlastRadiusExceeded`) and the warm-up grace period.

## 4. Recommendation

Ship a **per-role static-prior baseline with per-instance online adaptation**:

1. **Generalize `Baseline` to a keyed collection.** Introduce a `RoleId`
   (string newtype) and a `BaselineSet { role_priors: Map<RoleId, RoleBaseline>,
   default: RoleBaseline }`. `RoleBaseline` = today's three spectral envelopes
   **plus** a reference event-kind/capability histogram (B) and egress-cadence
   control limits (D). Resolve the active `RoleBaseline` by the agent's role at
   score time. Keep `default_baseline()` as the fallback role (coding/unknown).

2. **Back the trait with a per-agent online layer over the role prior.**
   `observe(agent, sample)` updates the agent's per-(role,dimension) EWMA
   mean/var, **shrinking toward the role prior** with weight decaying in sample
   count (hierarchical partial pooling). `assess(agent)` scores the agent's
   current profile against `shrinkage·role_prior + (1−shrinkage)·own_ewma`,
   returns `Deviant { score, dimension }` on the max-deviation dimension.
   Down-weight updates from samples that already scored `Deviant`
   (baseline-poisoning guard).

3. **Cold start = role prior + warm-up grace.** New agent starts *as its role*
   (shrinkage=1), capped at warn-class intervention for the first W sessions,
   converging to its own profile as evidence accrues.

4. **Reuse the scoring + distance code unchanged.** (A) via `Baseline::score`;
   the size-invariant comparison via `heat_kernel_distance`; the early-warning
   via `davis_kahan_ratio`. Net-new code is the *keying*, the *histogram /
   cadence* features, and the *EWMA+shrinkage* online layer — not new spectral
   math.

5. **Keep the boundary neutral (multi-consumer).** The `smb_envelope` side
   stays exactly the existing `observe`/`assess` + `BehaviorSample` /
   `Assessment` — **no SMB or role vocabulary leaks into the trait** (Whale
   Signal co-consumer). `RoleId` and the role→prior mapping live on the
   `ember-agent-monitor` impl + the consumer's config, not in the trait. The
   consumer tags each sample's `dimension` and supplies the role binding when
   it constructs the impl; the trait never names a role. (See §6, fork F1, for
   *where* the role binding is injected.)

This is the **minimum correct** build: it is per-role and per-instance,
solves cold-start, respects per-server isolation and the blast-radius bound,
and adds no new linear algebra. It defers peer-set (C) and any learned/ML
model until (A)+(B)+(D) are shown insufficient on real fixtures.

## 5. Decision points / forks (call these out before implementing)

**F1 — Where does the role↔baseline binding live?**
The trait is keyed by `AgentId` only; nothing maps an agent to a role or a
role to a baseline.
- (a) **Consumer supplies role at construction** — the monitor impl is built
  with an `AgentId → RoleId` resolver injected by the platform; trait
  unchanged. *(Recommended — keeps the trait neutral; SMB owns the agent
  catalog and roles anyway.)*
- (b) Add an `assess`/`observe` overload carrying role context — pollutes the
  neutral trait, hurts the Whale Signal co-consumer. *(Reject unless (a) proves
  unworkable.)*
- (c) Encode role inside the `AgentId` string convention — implicit, brittle.

**F2 — Spectral scoring: three-envelope decomposition vs single heat-kernel
distance.** Keep `Baseline::score`'s `(fiedler, spectral_dim, heat)` triple
(attributable, already shipped) **or** switch the spectral term to a single
`heat_kernel_distance` to a stored role-centroid profile (size-invariant, one
number, less attributable). *(Recommend: keep the triple for attribution;
expose the centroid-distance as a secondary dimension only if roles need
finer discrimination.)*

**F3 — Per-role-static baseline vs per-instance-adaptive baseline.** Pure
static role envelopes (simple, reproducible, can't drift) vs per-instance EWMA
(adapts, but can be slowly poisoned and drifts from "role normal"). *(Recommend
the hybrid: static role prior + shrinking per-instance EWMA — gets both, with
the poisoning guard. This is the central design choice; everything else
follows it.)*

**F4 — Where does role-prior data live, given per-server tenancy (§8.2)?**
- (a) **Shipped static role priors** (per-role `default_baseline()` analogues
  from internal/synthetic corpora) — zero cross-tenant flow, respects hard
  isolation. *(Recommended cold-start source.)*
- (b) **Per-tenant learned role prior** — aggregate this tenant's own agents
  on the tenant's server; richer, still isolation-clean; but a brand-new tenant
  has none (falls back to (a)).
- (c) Cross-tenant aggregated prior — **rejected** for live use under
  per-server isolation; only admissible as an *offline, anonymized* corpus that
  feeds (a) at release time, never a runtime read.

**F5 — Statistical (EWMA/SPC) vs spectral distance as the primary engine.**
They are complementary, not competing: spectral (A) for *shape*, EWMA (B)/(D)
for *mix and tempo*. Fork is really "do we ship (B)/(D) in P2 or spectral-only
first?" *(Recommend ship both — spectral-only repeats today's blind spot:
right shape, wrong verbs passes.)*

**F6 — Online update cadence & poisoning guard.** Update EWMA every event, every
session-end, or every `spectral_cadence` events? And: never update from a
`Deviant` sample, reduced-weight update, or always update? *(Recommend:
update at session-end on the session's aggregate; reduced-weight (not zero)
on `Deviant` sessions so a slow legitimate drift still registers but an attack
can't anchor the baseline to itself.)*

**F7 — Intervention coupling.** Does a baseline-deviation finding feed the same
global-mode ladder as pattern findings (one unified score → ladder), or a
separate "insider score" channel with its own thresholds + quarantine path?
*(Recommend unified scoring into spec §5's ladder, with quarantine as the
explicit escalation past block — but gate quarantine on the warm-up period +
blast-radius bound so a half-formed baseline can't DoS, per §8.6.)*

**F8 — Role granularity.** One baseline per *role* (receptionist), per
*(role, tenant)*, or per *agent definition version* (plan §8.12 versioning)?
*(Recommend per-(role) prior with per-(role,tenant) learned refinement (F4b);
revisit per-definition-version when the rollback mechanism §8.12 lands, since a
definition change legitimately shifts the baseline and shouldn't read as
anomaly.)*

## 6. Trait & impl shape (multi-consumer neutrality)

**Keep `smb_envelope::monitor` exactly as-is.** It is already the right
neutral boundary: opaque `BehaviorSample { dimension, value }` in,
`Assessment { Normal | Deviant { score, dimension } }` out, keyed by `AgentId`.
No change needed to satisfy P2 — which is the point of a multi-consumer
interface.

The `ember-agent-monitor` impl behind it (net-new, P2):
```
PerRoleBaseline {
    roles: Map<RoleId, RoleBaseline>,     // static priors (F4a) + learned (F4b)
    default: RoleBaseline,                 // = today's default_baseline(), coding/unknown
    resolve_role: Fn(&AgentId) -> RoleId,  // injected by consumer (F1a) — trait stays neutral
    online: Map<AgentId, AgentStats>,      // EWMA mean/var per dimension + sample count
}
impl BehavioralBaseline for PerRoleBaseline {
    fn observe(&self, agent, sample) { /* EWMA update, shrink→prior, poisoning-guard (F6) */ }
    fn assess(&self, agent) -> Assessment { /* score vs shrunk prior; max-dev dimension */ }
}
```
- `RoleBaseline` = `{ spectral: Baseline /* reuse */, kind_caps_ref:
  Histogram, egress_cadence: ControlLimits }`.
- `RoleId` and `resolve_role` live **here + in the consumer's config**, never
  in the trait — so Whale Signal binds its own entities to its own roles
  without inheriting SMB vocabulary.
- `Quarantine` impl is separate (already a separate trait); the baseline only
  *scores* — the decision to quarantine is the consumer's, bounded by
  `BlastRadiusExceeded` + warm-up (F7).
- **Fixture discipline (repo house rule):** every role prior and every
  documented insider-miss lands as a `threat-intel/fixture` with pinned
  `expected.json` (the receptionist-acting-strange case; the honest negative
  where shape is normal but capability-mix is off and spectral-only misses it).
  Calibration corpora grow `clean_corpus/` per role; bumps get a CHANGELOG entry.

## 7. Open questions

1. **Role taxonomy ownership.** The set of SMB roles (and their starter
   priors) is a *product* artifact, not a monitor artifact. Who authors the
   shipped per-role priors, and from what corpus, before real tenant data
   exists? (Ties to F4a; needs an SMB-side decision.)
2. **Definition-version vs baseline drift (plan §8.12).** A legitimate agent-
   definition change shifts the true baseline. Without §8.12's rollback/version
   mechanism, a redeploy will read as a deviation spike. Sequencing question:
   does per-agent baseline need version-awareness from day one, or can it ship
   with a "reset baseline on definition change" hook? (F8.)
3. **Warm-up window length W and shrinkage schedule.** No data yet to set W or
   the shrinkage decay rate; needs the first per-role calibration corpora to
   tune (analogous to how today's three global envelopes were fit).
4. **Egress-cadence windowing.** What time window for the EWMA tempo (per-hour?
   per-session?), and how to handle bursty-but-legitimate roles (scheduler
   sending many confirmations at 9am). Needs role-realistic temporal fixtures —
   which the current corpus (causal-topological, untimed) does not yet contain.
5. **Whale Signal co-input.** This doc is SMB-driven; the interface is held
   neutral, but the *role-prior + shrinkage* mechanism should be checked
   against a Whale Signal entity story before the impl freezes, so the online
   layer isn't quietly SMB-shaped.
